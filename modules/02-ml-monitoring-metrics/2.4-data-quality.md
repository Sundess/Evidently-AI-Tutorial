# 2.4 Data quality in ML

Garbage in, garbage out. Most production failures are data and pipeline bugs, not the model.

## What goes wrong

- **Wrong source** – pipeline points to an old table version.
- **Lost access** – permissions changed, data can't be read.
- **Bad SQL** – query breaks on edge cases (e.g. a user in another time zone acts "tomorrow").
- **Infrastructure update** – a library changes how something is computed.
- **Broken feature code** – fails on corner cases (e.g. a 100% discount).
- **Schema change / data loss** – broken logging, frozen sensor values.
- **Cascading failures** – a broken upstream model feeds bad inputs to downstream ones.

## What to monitor

Start with a **data profile** per feature: min/max, quantiles, unique values, most common values, share of missing. Compare current batch vs reference and decide alert conditions in advance.

## How to monitor

**No reference** – write rules from domain knowledge:

- no / low share of missing values
- no duplicate rows or columns
- no constant (or almost constant) features
- no highly correlated features
- no target leaks (feature very correlated with target)
- no range violations (negative age, negative sales)

**With reference** (training data or a past good batch) – generate expectations from it:

- schema and column types
- completeness (e.g. ≥ 90% non-empty)
- batch size (row count)
- column patterns: uniqueness (IDs unique, features not), ranges, descriptive stats (mean, median, quantiles)

Use both: rules where you know the domain, reference-based checks for everything else.

## Tips

- Check data quality **before** drift – broken data looks like drift.
- Auto-generated checks are strict. Tune them (e.g. row count differs between batches by design).
- Test feature code on edge cases.
